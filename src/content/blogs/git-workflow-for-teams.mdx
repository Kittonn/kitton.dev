# Git Workflow for Teams

Choosing the right Git workflow affects how fast your team ships, how many merge conflicts you fight, and how stable your main branch stays.

## Trunk-Based Development

The simplest workflow: everyone merges to `main` frequently (at least daily).

```
main: A---B---C---D---E---F
           \       /
            feat  (lived < 2 days)
```

### Rules

1. **Never** let a branch live more than 2 days
2. Use **feature flags** to hide incomplete features in production
3. **CI must be fast** — if the build takes 20 minutes, nobody merges frequently
4. Write **good tests** — `main` must always be deployable

```bash
# Start a tiny feature
git checkout -b feat/add-rss-link

# Work for a few hours, then merge
git checkout main
git merge --no-ff feat/add-rss-link
git push origin main

# Delete branch immediately
git branch -d feat/add-rss-link
```

## Feature Branch Workflow (GitHub Flow)

Better for teams that deploy on PR merge:

```
main:    A-----------D---E
              \     /
feature/auth:  B---C  (PR → squash merge)
```

### PR Size Matters

| PR Size | Review time | Merge conflicts | Quality |
| ------- | :---------: | :-------------: | :-----: |
| < 200 lines | Fast | Low | ✅ Good |
| 200–500 lines | Medium | Medium | ⚠️ OK |
| > 500 lines | Slow | High | ❌ Hard to review |

> **Rule of thumb:** If a PR takes more than 30 minutes to review, split it up.

## Merge Strategies

### `--no-ff` (Merge Commit)

```bash
git merge --no-ff feat/auth
```

```
* df3a2b1 Merge branch 'feat/auth'
|\
| * c4e1f23 feat: add email/password auth
| * a9d8e12 feat: add OAuth with Google
|/
* 7b2c891 chore: update dependencies
```

Preserves branch history. Good for **feature tracking**.

### Squash Merge

```bash
git merge --squash feat/auth && git commit -m "feat: add authentication"
```

```
* 8f2a1d3 feat: add authentication
* 7b2c891 chore: update dependencies
```

Clean linear history. Good for **many small commits during development**.

### Rebase

```bash
git rebase main feat/auth
git checkout main && git merge --ff-only feat/auth
```

```
* c4e1f23 feat: add email/password auth  (rebased)
* a9d8e12 feat: add OAuth with Google    (rebased)
* 7b2c891 chore: update dependencies
```

Cleanest history. Good for **open source** where commit history matters. Avoid on shared branches.

## Conventional Commits

Standardize commit messages for automated changelogs:

```
<type>(<scope>): <short description>

[optional body]

[optional footer]
```

### Types

| Type | Use for |
| ---- | ------- |
| `feat` | New feature |
| `fix` | Bug fix |
| `docs` | Documentation only |
| `style` | Formatting, no logic change |
| `refactor` | Refactor, no new feature or fix |
| `test` | Adding or fixing tests |
| `chore` | Tooling, deps, build |
| `perf` | Performance improvement |
| `ci` | CI/CD changes |
| `revert` | Reverting a commit |

### Examples

```bash
git commit -m "feat(auth): add magic link login"
git commit -m "fix(api): handle 429 rate limit response"
git commit -m "docs: add deployment guide to README"

# Breaking change
git commit -m "feat!: remove legacy v1 API endpoints

BREAKING CHANGE: The /api/v1/* routes have been removed.
Migrate to /api/v2/* before upgrading."
```

## Branch Protection Rules (GitHub)

Set these on `main`:

- [x] Require pull request before merging
- [x] Require at least 1 approving review
- [x] Dismiss stale reviews when new commits are pushed
- [x] Require status checks to pass (CI)
- [x] Require branches to be up to date
- [x] Restrict who can push to matching branches
- [ ] Require linear history (opinionated — use if you prefer rebase)

## Git Aliases Worth Adding

```bash
git config --global alias.st "status -sb"
git config --global alias.lg "log --oneline --graph --decorate --all"
git config --global alias.undo "reset --soft HEAD~1"
git config --global alias.wip "commit -am 'WIP'"
git config --global alias.unwip "reset HEAD~1"
```

```bash
# Usage
git lg    # visual branch graph
git undo  # un-commit last commit (keeps changes staged)
git wip   # quick save of in-progress work
```
